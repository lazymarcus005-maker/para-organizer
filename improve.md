## Historical / Legacy Notes — SQLite → PostgreSQL Migration Plan (v4 → v5)

*(Condensed from an ~650-line, 5-phase migration plan originally written on this branch. Original context: at the time this was written, `main` was still the SQLite single-container version and `features/upgrade` was an experimental branch that a "HARD RULE" said must **never** be merged into `main`. That rule is now obsolete — the PostgreSQL + Redis + Worker + Scheduler architecture described below was in fact adopted and is what actually runs in production today, deployed via Dokploy rather than the manual docker-compose + external `marcusx13db` host provisioning steps the plan originally described. Treat all commands, ports, and service names below as historical — for current values see the live `docker-compose.yml` and `app/config.py` on `main`.)*

What the plan covered, roughly:

- **Phase 0 (pre-flight bug fixes):** `scheduler_service.py` was pushing task-queue topics (`archive`, `autonomy`) that didn't match any registered handler/topic, so those scheduled jobs were failing silently. Fix was to rename them to `classify` and `escalate`. Also flagged a need to diff the live SQLite schema against `scripts/migrate_pg.py`'s expected `TABLES` list before migrating.
- **Phase 1 (infra fixes):** `docker-compose.yml` had a `container_name` + `deploy.replicas>1` conflict (Compose rejects that combo) and an obsolete `version:` key; added a `.env.example` template; fixed the Dockerfile `HEALTHCHECK` to hit a lightweight `/api/health/live` instead of `/api/stats`; added a `wait-for-it.sh`-style startup gate so app/worker didn't race Postgres/Redis on boot.
- **Phase 2 (worker logic port):** 7 of 8 worker handlers (`classify`, `embed`, `notify`, `link`, `distill`, `review`, `escalate`) already had real implementations in SQLite-era modules (`app/classifier.py`, `app/embed.py`, `app/notifier.py`, `app/linker.py`, `app/distill.py`, `app/review.py`, `app/scheduler.py`) and just needed porting from `aiosqlite`/`app.database` to async SQLAlchemy/`app.database_v2` + `pgvector`. `handle_backup` had no prior implementation and was written from scratch (`app/backup.py`: `pg_dump` + S3-compatible upload).
- **Phase 3 (data migration):** `scripts/migrate_pg.py` (asyncpg + aiosqlite, batched inserts, row-count verification) migrated `notes, links, history, notifications, settings, chat_messages, llm_usage, events, tasks, items, feedback`. Embeddings were skipped in favor of a backfill job; FTS5 data was skipped since PostgreSQL `tsvector` is auto-generated.
- **Phase 4-5 (deploy + verify):** provisioning steps against an external `marcusx13db`-hosted Postgres/Redis (superseded — production Postgres is now its own dedicated host, and deployment is via Dokploy, not manual `docker compose`/`docker exec` commands), plus smoke tests (`/api/health/live`, `/api/health/ready`, `/api/health`), CRUD/search endpoint checks, row-count parity checks, and a rollback plan (restore the old SQLite container from a `para.db.backup.*` snapshot).

For the actual current schema, handlers, and deployment process, refer to the live code on `main` and to `docker-compose.yml` rather than this section. For the full original SQLite-era implementation, see branch `backup/sqlite-version`.
